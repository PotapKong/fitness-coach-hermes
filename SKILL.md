# Fitness Coach for Hermes

This is a **portable Agent Skill** and local-first logging companion to the official Hermes `fitness-nutrition` skill (`official/health/fitness-nutrition`). Install both on Hermes; on other agents this package works independently for logging and USDA lookup. Upstream provides exercise guidance and offline TDEE calculators; this package provides a unit-checked USDA food lookup, records confirmed values, creates weekly cards and selects source-linked morning candidates. Never claim this companion diagnosed a condition or sent a message automatically.

## First-use safety and consent

- Ask whether the person wants persistent **local** fitness logs. Do not log health data until they consent. Use a private data directory outside git (`COACH_DATA_DIR`); never commit real logs, photos or measurements. Do not mix multiple people's data in one directory.
- Ask for a goal and limitations (including conditions, pain, pregnancy, history of disordered eating) before suggesting a training or calorie target. Refer clinical, eating-disorder or concerning symptoms to a qualified professional. No exercise through acute pain, and no extreme caloric deficits or automatic goals from a photo.
- Daily calories from a food photo are an **uncertain estimate**, especially for portions, oils and sauces. Ask for package labels/weights or the user's confirmation. State source and uncertainty; do not fabricate exact macros. USDA entries are per 100 g; scale by a confirmed portion using a calculator tool, not mental arithmetic.
- Keep medical and personal details out of the Telegram card. Send only to the clearly specified chat/topic when the user requests delivery, never to a group or third party by default.
- Use population guidance only with context, not as a personal prescription; do not set a default deficit, supplement dose or forced training progression. A micronutrient chart cannot diagnose deficiency. See `EVIDENCE.md` for primary sources, scope and compared skills.
- For a more polished AI-generated report, follow `VISUAL.md` exactly: explicit consent before sending private records to an external image service, exact-data readback, and neutral colors unless a user-approved **weekly-average range** and all seven confirmed-complete food days justify a status. The code compares recorded energy to a user range but does not score diet quality. Never call an attractive image a validated chart without checking every value and bar.
- Ask for a visual *taste*, not a gender stereotype. Offer `bold-athletic`, `high-energy`, `editorial`, `minimal` or `adaptive`, and whether food scenes should be literal, abstract or playful. Only save owner-chosen options with `visual-profile --style ... --food-scene ... --confirmed-by-user`. Style preference is **not** consent to upload personal food/weight records to an image provider. Never infer a person's body, gender, health or amount eaten from recorded weight or calories.

## Workflow

Resolve `SKILL_DIR` to the directory containing **this** SKILL.md (not the current working directory), then invoke `python3 "$SKILL_DIR/coach.py"`. Set `COACH_DATA_DIR` to a per-person private directory outside the public repository. On Hermes the installed file normally lives under `~/.hermes/skills/fitness-coach-hermes/`; other agents may use different paths. The code is public, but journal data remains local. The durable `journal.json` is authoritative and each write mirrors the entire history into private `journal.sqlite3` with indexed entries, corrections and complete days. Neither is session context or Hermes memory; read only the date range and fields needed for the current answer. If a database sync fails after a JSON write, preserve JSON and retry `history_db.py sync`; if SQLite itself is corrupt, obtain owner approval and run `history_db.py repair --confirmed-by-user` to quarantine the old index and rebuild it from JSON. The CLI rejects concurrent writers via a lock; use a stable `--event-id` on each incoming log message to prevent retry duplicates.

1. For exercise names and TDEE, load `fitness-nutrition` if installed (`hermes skills install official/health/fitness-nutrition` after reviewing its scope). Do not mistake its BMI/TDEE estimate for a diagnosis or a measured energy expenditure. **Do not use upstream `nutrition_search.py` for calories:** it selects nutrients by name only and can mistake kJ for kcal (e.g. USDA FDC 171287, 599 kJ vs 143 kcal). For food data run `python3 "$SKILL_DIR/food_lookup.py" "food name"`, which matches energy by kcal unit. It uses `DEMO_KEY` unless `USDA_API_KEY` is set. Never convert a null nutrient to zero.
2. Ask the user to confirm portions/macros before logging. Log a meal with an explicit source:
   `python3 "$SKILL_DIR/coach.py" --data-dir "$COACH_DATA_DIR" meal --date YYYY-MM-DD --name "..." --grams N --kcal N --protein N --fat N --carbs N --source label|usda|user|photo-estimate`
   `--grams` is optional and only for a confirmed weighed portion. Do not derive mass from energy. **Omit `--kcal` if unknown**, even when a meal was logged; do not encode missing energy as `0`. Literal zero needs independent confirmation.
   For a USDA result, compute values for the actual weighed portion; include the FDC identifier and serving in the meal name if possible.
3. Log a weighed USDA food with `food --fdc-id ID --grams G` only after matching the exact product/preparation; this records units, portion, macros and available micronutrients. For a manual estimate use `meal` and mark the source. Missing values remain unknown (`null`), not zero. Do not equate one database entry with a whole dish or treat `0` on an incomplete log as actual intake.
4. Log exercise via `workout --name "..." --minutes N` (optionally all of `--sets N --reps N --load-kg N`), weight via `weight --kg N`. Set `target --kcal N --confirmed-by-user` only for an adult after the owner chooses it; optionally include both `--weekly-avg-min N --weekly-avg-max N` for an owner-chosen weekly-average energy range. The CLI rejects outlier inputs but does **not** declare accepted values safe. For a confirmed mistake, use `correct-entry --event-id ORIGINAL --correction-id UNIQUE --field kcal --value 450 --confirmed-by-user`; use `--value unknown` for an uncertain optional numeric field. For a wrong USDA item/portion, use `void-entry --event-id ORIGINAL --correction-id UNIQUE --reason "..." --confirmed-by-user`, then re-log the verified item under a NEW event ID. Corrections retain private before/after history and reopen a food day; never quietly add a duplicate. New records receive immutable local event IDs if none were provided; for old records without an ID, `migrate-legacy-ids --confirmed-by-user` assigns IDs and prints a private index/date/type mapping for exact verification. Repeated IDs are refused.
5. On **every new entry**, run `snapshot --scope entry --date YYYY-MM-DD --event-id THE_SAME_STABLE_ID` and return a concise receipt plus today's recorded subtotal; do not accidentally select a different late entry. Only send a GPT Image card if the owner opted in to external image processing. At **day end**, run `snapshot --scope day` for today's entries plus a short Monday-to-today line; run `close-day --confirmed-by-user` only if the owner confirms all food is logged. At **week end** (ISO Monday–Sunday), run `snapshot --scope week`; compare observed activity only to verified population guidance with intensity context, never turn daily nutrient references into a weekly allowance. A calorie average includes only owner-confirmed complete days **with kcal known for every logged food**; partial totals keep their coverage labels. See `VISUAL.md` for distinct card art directions and data-readback gates. Never set up scheduled delivery without timezone, time and destination approval.
   Each snapshot contains `recorded_food_items` and `recorded_workout_items`: draw only foods/exercises actually named for that period, and verify every visual object. If the journal says “lunch” but doesn't identify ingredients, depict no invented dish and **no empty plate**; use typography or another neutral scene. For many entries use a spread/collage of named foods; a bucket/mountain is an explicitly labelled metaphor only if the owner chose `food_scene=playful`, never a literal volume inferred from calories. Do not equate masculinity with food size or training intensity.
6. For a local text report run `report --date YYYY-MM-DD`; for 7/14/28/90-day machine-readable dynamics run `trends --date YYYY-MM-DD --days N`. For **all-time history**, run `python3 "$SKILL_DIR/history_db.py" --data-dir "$COACH_DATA_DIR" history --from-date YYYY-MM-DD --to-date YYYY-MM-DD --limit 50 --offset 0` (omit date bounds only if the owner really requests all years; page through `has_more`). For monthly progress run `python3 "$SKILL_DIR/history_db.py" --data-dir "$COACH_DATA_DIR" progress --limit 12 --offset 0`, which distinguishes complete known-kcal days, partial records, workouts and weight observations. Both commands first sync the SQLite index from the private JSON under a lock, including older pre-database journals; never dump the whole DB into the chat or permanent agent memory. For a deterministic fallback card run `card --date YYYY-MM-DD --view nutrition|activity|micros|micro-trend --nutrient iron_mg --output /absolute/private/path/card.png`. Inspect numbers, missing days and privacy. `micro-trend` scales to recorded max, not RDA. Never diagnose deficiency or suggest supplements/doses from the journal.
7. When the user asks for a Telegram update, send the **verified card** as a native image to the exact chat/thread with a short text summary. In a direct Hermes reply, `MEDIA:/absolute/private/path/card.png` sends a standalone image. For other agents use their native attachment tool. For a different destination use a supported, verified route and read it back. Do not assume `MEDIA:` plus body becomes a photo caption.
8. Offer **separate, opt-in** daily morning ideas and gentle missing-log reminders. For ideas, first ask tastes, allergies/exclusions, kitchen constraints, available time and safe activity preferences; store a minimal private profile only after consent. Use `python3 "$SKILL_DIR/ideas.py" --profile /private/profile.json --date YYYY-MM-DD` for a read-only, source-linked recipe candidate. Never present short ingredient hints as allergen-safe: when allergies/exclusions exist, this picker returns no recipe pending full verification. Activity ideas require confirmed preferences and limitation review; no exercise prescriptions. `automation_core.py` now stores explicit subscriptions, enforces local time/quiet hours, reserves per-day deliveries and rechecks consent/journal before send; **it does not send messages or create Hermes jobs**. A platform adapter still must send, read back the exact destination/message ID, then acknowledge. See `AUTOMATION.md`. Do not promise active reminders without an approved route, tested adapter and exact subscription. Never silently schedule or send history to another service. Never push `private-data/`, real user-derived cards, profiles or health logs to a repository; the tracked examples here are synthetic, reviewed showcase assets only.
9. The independent **repository-update cron** is documented in `UPDATES.md`. It may be created at installation if the owner explicitly requests unattended sync from the named public source; it never sends health messages and must not touch `COACH_DATA_DIR`. The automatic updater follows GitHub `main` code, so explain supply-chain trust and offer a review-only `--check` alternative.

## Delivery and validation

Run `python3 -m unittest discover -s tests -v`; smoke test `report` and `card` in a temporary data directory. Open the card and check mobile legibility; totals must match the report. Live Telegram delivery is verified only after the user asks for a specific send and the exact message is read back. See `README.md` for setup and examples.
